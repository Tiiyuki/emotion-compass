# AI対話型自己理解支援サービス（仮称）

> **README更新版（講師レビュー前）**：サービス名は仮称です。

## 1. サービス概要

**サービスコンセプト：「自分の機嫌は、自分でとれる。」**


仕事や人間関係の悩みを抱え、自分がなぜつらいのか、その根本原因が分からない人に向けたAI対話型の自己理解支援サービスです。

AIとの対話を通じて、表面的な悩みだけでなく、その背景にある感情・価値観・過去の経験などを掘り下げ、利用者自身も気づいていなかった根本的な要因を探ります。自分の気持ちをうまく言葉にできなくても、選択肢と自由入力を使い分けながら対話できます。

AIが提示する解釈や仮説を利用者自身が確認・訂正し、納得した段階で感情面・問題面の対処方法を選べるようにすることで、自分の気持ちを理解し、状況に応じて対処する力を育むことを支援します。

## 2. このサービスを作りたいと思ったきっかけ

### 2-1. きっかけ

仕事や人間関係でつらい出来事が起きたとき、出来事そのものは説明できても、「なぜこれほどつらいのか」「自分は何に傷ついたのか」を言葉にするのは難しいことがある。話を聞いてもらうだけでは整理しきれない感情の背景を、焦らず丁寧に探れる手段があればと考えたことが、制作の出発点である。


### 2-2. なぜ気になったのか

同じような出来事でも、人によってつらく感じる理由は異なる。表面的な出来事への対処だけでなく、その人が何を大切にし、どのような経験や考え方を持っているかを見つめることで、悩みの根本的な要因に近づけるのではないかと考えた。AIの解釈を一方的に受け入れるのではなく、利用者自身が確かめ、違えば訂正できる仕組みによって、納得できる自己理解を支援したい。


## 3. 解決したい課題

### 3-1. 最初の困りごと

仕事や人間関係でつらい出来事があったとき、自分がなぜこれほどつらいのかをうまく言語化できない。

### 3-2. 本当に解決したい課題

表面的な出来事や感情への対処にとどまり、悩みの背景にある価値観や経験、反応の傾向を十分に理解できないため、自分に合った対処方法を見つけにくいこと。また、AIへの指示や気持ちの言語化が苦手な場合、対話を深めるための質問を自分で考えることが負担になる。


## 4. 想定ユーザーと利用体験

### 4-1. 想定ユーザー

仕事や職場の人間関係によるストレスを抱える20〜40代の社会人を、初期の想定ユーザーとする。特に、嫌な出来事のあとに感情を整理できず、なぜ自分がつらいのかを理解したい人を想定する。

### 4-2. 自分と想定ユーザーとの距離

仕事や人間関係の悩みについて、自分自身の経験や身近な相談を通じて課題を身近に感じている。一方で、悩み方や求める支援は人によって異なるため、自分の経験だけで需要を判断せず、想定ユーザーへのヒアリングを通じて確かめていく。

### 4-3. 使う人がいそうか確かめる

**最初に利用してくれそうな人**：仕事や職場の人間関係によるストレスを抱えている20〜40代の社会人。身近な人から、職場の人間関係や理不尽な扱い、仕事のプレッシャーについて相談を受けた経験がある。

**利用を思い出す場面**：仕事で嫌な出来事があったとき、自分がなぜつらいのか分からないとき、余裕があるときに過去の経験を振り返りたいとき、日常的に自己理解を深めたいとき。

**現在の対処方法**：誰かに相談する、我慢して時間が解決するのを待つ、ChatGPTなどの生成AIを使う。ただし、一般的な助言が本人の状況に合わなかったり、根本的な要因に気づかないまま終わったりする場合がある。

**このサービスを選ぶ理由（仮説）**：一方的な解決策ではなく、質問を通じて本人が気づいていない背景や価値観を探り、理解したことを蓄積し、次の行動につなげる体験を提供する。

**今後の検証**：身近な相談経験者などへのヒアリングを通じ、利用意向や既存AIチャットとの違いに価値を感じるか確認する。主治医からもニーズや差別化について問いが出ており、需要は未検証の仮説として扱う。

### 4-4. 利用開始から継続まで

利用者は、仕事や人間関係でつらい出来事があったときにサービスを開き、選択肢または自由入力でAIとの対話を始める。言葉にしにくい場合はAIが質問を言い換えたり、選択肢を提示したりする。AIの理解に違和感があれば訂正し、納得できる仮説を一緒に探る。利用者が納得できた段階で、感情面・問題面の対処方法を複数提示し、利用者自身が試す方法を選ぶ。必要に応じて過去の相談を振り返り、以前の気づきを次の対処に活かす。

## 5. 既存サービスとの比較・差別化

### 5-1. 類似サービスとの比較

本サービスと関連する既存サービスとして、Rosebud、Wysa、Finchを比較する。

| 既存サービス | 既存サービスの主な特徴 | 本サービスが特に重視する点 | 本サービスを利用するメリット（目指す価値） |
| --- | --- | --- | --- |
| Rosebud | AIとの対話による日記・振り返りや、過去の記録からのパターン発見 | AIが提示した悩みの原因について、利用者が確認・訂正しながら深掘りする | **AIの解釈を鵜呑みにせず、自分が納得できるまで悩みの背景を探れる** |
| Wysa | AIとの対話による感情の整理や、セルフケア・対処スキルの支援 | 悩みの背景について利用者の納得を確認してから、対処方法を提案する | **自分の気持ちや悩みを十分に理解したうえで、納得できる対処方法を選べる** |
| Finch | ペット育成や目標管理を通じたセルフケアの習慣化 | 日々の習慣化よりも、一つの悩みを掘り下げて背景にある要因を探る | **目の前の悩みについて、なぜつらいのかを整理し、具体的な対処につなげられる** |

#### 本サービスならではの提供価値

本サービスは、既存サービスにも見られるAI対話や自己理解支援の機能を活用しながら、**AIへの相談が苦手な人でも、自分が納得できる答えと対処方法を探せること**を重視する。

特に、以下の3つを一連の利用体験として提供する。

1. **言葉にできなくても相談できる**  
   選択式と自由入力を併用し、AIが質問を調整することで、利用者のAI活用スキルや言語化能力による負担を軽減する。
2. **AIに決めつけられず、自分の気持ちを理解できる**  
   AIの解釈を確認・訂正しながら対話を進めることで、利用者自身が納得できる理解を探る。
3. **自分に合った対処方法を選べる**  
   悩みの背景について納得した後に、感情面と問題面の対処方法を提示し、利用者自身が次の行動を選択できる。

これにより、サービスコンセプトである「自分の機嫌は、自分でとれる。」の実現を目指す。

なお、既存サービスにも類似機能が存在する可能性があるため、機能の独自性や優位性を断定するのではなく、本サービスが特に重視する利用体験と提供価値を比較している。記載したメリットは設計上の目標であり、利用者テストで検証する。

### 5-2. 自分が作りたい理由

一般的なAIチャットでは、利用者の発言からAIが解釈を作っても、その理解が正しいかを継続的に確かめ、訂正を整理して次の相談に反映する体験が十分に構造化されていない場合がある。そこで、AIの解釈を利用者自身が確認・修正できる仕組みを中心に据えたい。

### 5-3. 提供する体験の違い

単に共感や一般的なアドバイスを返すのではなく、悩みの背景にある要因を質問で掘り下げる。AIの仮説に対し「納得できる」「少し違う」「分からない」と回答でき、違いを訂正した場合はAIが確認してから次に進む。**AIが正解を決めるのではなく、利用者が自分の理解を深める過程を支援する**点を特徴とする。

また、AIを使い慣れているかどうかや、気持ちを文章にできるかどうかによって利用しやすさが大きく左右されないことを目指す。選択式と自由入力を併用し、曖昧な回答や「分からない」という回答には、AIが質問を言い換えたり具体例を示したりする。利用者が納得した後には、気持ちを整える方法と状況に働きかける方法を提案し、本人が選べるようにする。

## 6. 提供する価値

### 6-1. 利用者の変化

- **行動**：選択肢や自分の言葉でつらい出来事を表現し、背景を振り返り、自分に合う対処方法を選べる。
- **気持ち**：理解できないつらさを抱え込むだけでなく、自分の反応を少しずつ理解できる。
- **考え方**：出来事そのものと、自分の解釈・感情・価値観を分けて考えられる。

### 6-2. 一文で表す提供価値

仕事や人間関係の悩みを抱える人が、AIの使い方や言語化の得意不得意にかかわらず、AIと認識をすり合わせながら悩みの背景を探り、自分に合った感情面・問題面の対処方法を選べるようになる。

## 7. MVPと本リリースの機能

### MVP（価値を検証するための最小版）

1. AIとの相談チャット（選択式・自由入力の併用）
2. 回答に応じた質問の調整（言い換え・選択肢・具体例の提示）
3. AIの解釈に対する確認・フィードバック・訂正
4. 対話を通じた悩みの背景・原因の掘り下げ
5. 利用者の納得後に行う対処方法の提案・選択（感情面・問題面から2〜3案）
6. 相談履歴の保存・閲覧
7. 過去の相談を必要に応じて参照する機能

対処方法は「試してみたい」「別の方法がいい」「今は考えたくない」から選べるようにし、提案を押しつけない。利用者がまだ納得していない場合は、対処方法の提案を急がず、対話の継続や終了を選べるようにする。

過去の相談がなくても現在の相談だけで深掘りを進められるようにする。過去の情報を参照する際は利用者の確認を取り、現在の発言と矛盾する場合は現在確認された内容を優先する。

### MVP後に検討する機能

対処方法を実践した結果の記録・効果分析、相談傾向の振り返り・分析、日記機能、自己理解の進捗を可視化する仕組みなど。相談回数の多さを悩みの深刻さと同一視しない。

## 8. 想定する懸念と対策

| 懸念 | 対策 |
| --- | --- |
| AIが誤った解釈を断定する | 仮説として提示し、利用者の確認・訂正を受ける |
| AIへの指示や言語化が難しい | 選択肢と自由入力を併用し、質問の言い換えや具体例を用意する |
| 利用者が納得する前に対処方法を押しつける | 納得度を確認し、提案の保留・変更・終了を選べるようにする |
| 訂正した内容が次の応答に反映されない | 確認済みの事実・否定された解釈・未確認事項を分けて管理する |
| 過去の相談に引きずられる | 参照前に確認し、現在の利用者の回答を優先する |
| 個人的な相談内容の漏えい | 認証、ユーザー単位のアクセス制御、HTTPS、秘密情報管理、保存・削除方針を設ける |
| 医療的な診断と誤解される | 診断を目的としないことを明示し、必要に応じ専門家への相談を促す |
| API料金や応答遅延 | 使用量を監視し、エラー時の案内や待機表示を用意する |
| 利用者ニーズが不明確 | 架空の相談シナリオによる品質検証と、対象者へのヒアリングを行う |

## 9. 今後の展開

MVPでAIとの深掘り対話と認識のすり合わせが有用か検証した後、相談履歴から利用者自身が振り返れる傾向表示を検討する。その後、日常の気づきを残す日記機能や、自己理解の変化を振り返る機能へ拡張する。高度な類似相談検索は必要性を確かめてから検討する。

## 10. 技術スタック

### 10-1. 使用予定の技術

| 用途 | 技術 |
| --- | --- |
| フレームワーク | Ruby on Rails |
| データベース | PostgreSQL |
| 動的な画面更新 | Hotwire（Turbo / Stimulus） |
| 認証 | Devise（メールアドレス＋パスワード） |
| AI対話 | OpenAI API（モデルは品質検証後に決定） |
| 公開先 | Render |

### 10-2. 技術選定の比較検討

| 分野 | 採用候補・方針 | 比較対象と選定理由 |
| --- | --- | --- |
| Webフレームワーク | Ruby on Rails | Djangoも可能だが、外部LLM APIを使うためPythonの機械学習ライブラリは必須でなく、Railsでデータ管理・画面更新を一貫して開発しやすい |
| DB | PostgreSQL | MySQLでも基本機能は実現可能。JSONBと将来のpgvector活用の選択肢を考慮 |
| 画面更新 | Hotwire | ReactよりRails中心の構成を維持しやすく、MVPのチャット・訂正画面に適する |
| 認証 | Devise | Rails標準の認証機能と比較し、既存の認証機能を活用して実装負担を抑える。認可は別途実装する |
| 公開先 | Render | AWS（特にEC2を使う構成）よりサーバー管理の負担を抑え、アプリ完成を優先する |
| LLM | OpenAI API | 質問の深さ・訂正への対応・費用・データ取扱条件を検証して最終モデルを選ぶ |

**挑戦したい点**：選択式と自由入力の併用、利用者の回答に応じた質問調整と深掘り対話、仮説へのフィードバック、訂正内容の保存と再利用、納得後の対処方法の提案・選択、過去の相談の適切な参照。

**不安な点**：AIの深掘り品質、解釈の誤り、利用者の納得度を適切に扱えるか、API応答時間、個人情報保護、API・公開環境の料金。

### 10-3. キャッチアップと開発方針

1. RailsとPostgreSQLで認証・相談履歴などの土台を作る。
2. OpenAI APIの基本的な送受信を小さく検証する。
3. Hotwireでチャット画面を段階的に更新する。
4. AIの仮説に対する確認・訂正と、その反映を実装する。
5. 利用者の納得を確認してから、対処方法の提案・選択を実装する。
6. 基本対話が完成してから過去の相談の参照を追加する。

DeviseとHotwireは実装時にRails・Rubyとのバージョン互換性、更新状況、サポート情報を確認する。Renderの無料PostgreSQLは保存期間やバックアップに制限があるため、実データを扱う公開時には適切な有料構成やバックアップ・削除方針を確認する。開発・動作確認には架空の相談データを使用する。
