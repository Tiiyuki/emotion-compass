# emotion-compass（エモーション・コンパス）

AIとの対話を通じて、自分の感情の背景を理解し、自分に合った対処方法を見つける自己理解支援サービスです。

## 1. サービス概要

**サービスコンセプト：「自分の機嫌は、自分でとれる。」**


仕事や人間関係の悩みを抱え、自分がなぜつらいのか、その根本原因が分からない人に向けたAI対話型の自己理解支援サービスです。

AIとの対話を通じて、表面的な悩みだけでなく、その背景にある感情・価値観・過去の経験などを掘り下げ、利用者自身も気づいていなかった根本的な要因を探ります。自分の気持ちをうまく言葉にできなくても、選択肢と自由入力を使い分けながら対話できます。

AIが提示する解釈や仮説を利用者自身が確認・訂正し、納得した段階で感情面・問題面の対処方法を選べるようにすることで、自分の気持ちを理解し、状況に応じて対処する力を育むことを支援します。

## 2. このサービスを作りたいと思ったきっかけ

### 2-1. きっかけ

私は、自分がやりたいと思って選んだIT業界で働く中で、上司との関係や業務の難しさに悩んだ経験があります。

サービスマネージャーとして運用設計業務に携わる機会があったとき、ネットワーク構築担当者から全体スケジュールの説明を受けた後、
お客様側の上司から業務内容を理解できたか確認されました。

私は認識のずれを防ぐために「一度通話して認識合わせをしたい」と伝えました。
しかし、「全然理解していないってことがわかりました。もういいです、僕がやります」と言われ、運用設計業務を担当できなくなりました。

確認しようとしただけなのに理解していないと決めつけられたことが悔しく、さらに、自分の成長や市場価値の向上につながると考えていた仕事を失ったことにも、
怒りや悲しさを感じました。

当時は「こんな案件にいる意味があるのだろうか」「いつになったら市場価値の上がる仕事を任せてもらえるのだろうか」と考え、仕事への意欲を失っていました。

その後、自社のカウンセラーに電話で相談しました。カウンセラーからは、理不尽な状況に腹が立つのは当然だと気持ちを受け止めてもらったうえで、
相手を変えることは難しいため、自分の感情をコントロールし、通常通り業務を行えるようになることが会社から求められていると説明されました。

その言葉を聞いて、私は気持ちが落ち着き、納得することができました。

一方で、夜に一人で悩んでいるときや、休日にも仕事のことばかり考えてしまうときには、もっと気軽に相談できる相手がいたらよいのにと感じていました。

こうした経験から、誰かに相談することで自分の気持ちや状況を整理できることの価値を実感するとともに、一人で悩んでいる時間にも、対話を通じて自己理解を深め、納得できる対処方法を考えられるサービスを作りたいと思いました。

### 2-2. なぜ気になったのか

私が大切にしているのは、自分の感情を理解したうえで、他人に決められるのではなく、自分自身が納得できる選択をすることです。

仕事でつらい出来事があったとき、何に不満を感じているのかはある程度分かっていても、なぜそれほど傷ついたのか、
背景にどのような期待や価値観があるのかまでは、簡単に整理できないことがありました。

また、悩みを抱えているときには、感情を理解するだけでなく、今の環境で働き続けるべきなのか、これからどう行動するべきなのかと迷うこともありました。

実際にカウンセラーとの対話によって気持ちが落ち着き、納得できた経験から、誰かと話しながら自分の感情や状況を整理することには価値があると感じています。

だからこそ、AIが一方的に原因や解決策を決めつけるのではなく、質問を重ねながら悩みの背景を掘り下げ、
利用者自身がAIの解釈を確認・訂正できる仕組みを作りたいと考えました。

利用者が自分の感情や価値観への理解を深め、自分自身で納得できる対処方法を見つけられるよう支援したいです。


## 3. 解決したい課題

### 3-1. 最初の困りごと

仕事や人間関係でつらい出来事があったとき、自分がなぜこれほどつらいのかをうまく言語化できない。

### 3-2. 本当に解決したい課題

表面的な出来事や感情への対処にとどまり、悩みの背景にある価値観や経験、反応の傾向を十分に理解できないため、自分に合った対処方法を見つけにくいこと。また、AIへの指示や気持ちの言語化が苦手な場合、対話を深めるための質問を自分で考えることが負担になる。
その結果、人間関係の悩みに気持ちを奪われ、自分が本来やりたいことや目標に向けて行動できなくなる場合がある。悩みの背景を理解し、自分で納得できる対処方法を選ぶことで、目標に向けて再び行動できるよう支援したい。


## 4. 想定ユーザーと利用体験

### 4-1. 想定ユーザー

人間関係の悩みが頭から離れず、自分が本来やりたいことや目標に向けて行動できなくなっている20〜40代の社会人を、初期の想定ユーザーとする。特に、嫌な出来事のあとに感情を整理できず、なぜ自分がつらいのかを理解したい人を想定する。

20〜40代を中心に想定するのは、自分自身も職場の人間関係に悩み、仕事で実現したかったことに向かって進めなくなった経験があり、課題や利用場面を具体的に捉えやすいためである。

MVPでは、人間関係の悩みを整理することを通じて、利用者が自分の感情や価値観を理解し、目標に向けて次にどう行動するかを自分で選べるかを検証する。

ただし、利用対象を20〜40代に限定するものではなく、将来的には幅広い年代や悩みに対応することも検討する。


### 4-2. 自分と想定ユーザーとの距離

私はIT業界で働く中で、上司との関係や業務の難しさに悩み、仕事への意欲を失った経験がある。
その際、自社のカウンセラーに相談したことで気持ちが落ち着き、今後の向き合い方について納得できた。

こうした経験から、私自身も仕事や人間関係の悩みを抱える想定ユーザーの一人であり、一人で悩みを抱え、誰かに相談したいと思う気持ちを実感している。

一方で、同じように仕事や人間関係で悩んでいても、その原因や求める支援は人によって異なる。
そのため、自分の経験だけを基準にするのではなく、想定ユーザーへのヒアリングを通じて、どのような場面で、どのような支援が求められているのかを確かめたい。

### 4-3. 使う人がいそうか確かめる

**最初に利用してくれそうな人**：人間関係の悩みが頭から離れず、自分が本来やりたいことや目標に向けて行動できなくなっている20〜40代の社会人。
身近な人から、職場の人間関係や理不尽な扱い、仕事のプレッシャーについて相談を受けた経験がある。


**利用を思い出す場面**：仕事で嫌な出来事があったとき、自分がなぜつらいのか分からないとき、余裕があるときに過去の経験を振り返りたいとき、日常的に自己理解を深めたいとき。

**現在の対処方法**：誰かに相談する、我慢して時間が解決するのを待つ、ChatGPTなどの生成AIを使う。ただし、一般的な助言が本人の状況に合わなかったり、根本的な要因に気づかないまま終わったりする場合がある。

**このサービスを選ぶ理由（仮説）**：一方的な解決策ではなく、質問を通じて本人が気づいていない背景や価値観を探り、理解したことを蓄積し、次の行動につなげる体験を提供する。


想定ユーザーへの検証は、行きつけのBARの店主に事前に相談し、了承を得たうえで、来店するお客さんに任意で協力をお願いする。人間関係の悩みによって、自分の目標に向けた行動が難しくなった経験がある人を中心に、3〜5人程度のヒアリングを目指す。

ヒアリングでは、実際に悩んだ場面、目標への影響、普段の対処方法、既存の相談手段で困ったこと、どのような支援があれば役立つかを確認する。

MVP完成後は、協力してもらえる人にアプリを試してもらい、AIの解釈が違っても対話を続けられたか、自分の感情や価値観を理解できたか、目標に向けた次の行動を自分で選べたかを確認する。

ヒアリングや利用テストは本人の同意を得て実施し、回答を強制せず、個人的な相談内容のプライバシーに配慮する。

### 4-4. 利用開始から継続まで

利用者は、仕事や人間関係でつらい出来事があったときにサービスを開き、選択肢または自由入力でAIとの対話を始める。言葉にしにくい場合はAIが質問を言い換えたり、選択肢を提示したりする。AIの理解に違和感があれば訂正し、納得できる仮説を一緒に探る。利用者が納得できた段階で、感情面・問題面の対処方法を複数提示し、利用者自身が試す方法を選ぶ。
MVPでは一つの相談の中で悩みを整理し、対処方法を選ぶ体験を提供する。
MVP完成後は、必要に応じて過去の相談を振り返り、以前の気づきを次の対処に活かせるようにする。


## 5. 既存サービスとの比較・差別化

### 5-1. 類似サービスとの比較

本サービスと関連する既存サービスとして、Rosebud、Wysa、Finchを比較する。

| 既存サービス | 既存サービスの主な特徴 | 本サービスが特に重視する点 | 本サービスを利用するメリット（目指す価値） |
| --- | --- | --- | --- |
| Rosebud | AIとの対話による日記・振り返りや、過去の記録からのパターン発見 | AIが提示した悩みの原因について、利用者が確認・訂正しながら深掘りする | **AIの解釈を鵜呑みにせず、自分が納得できるまで悩みの背景を探れる** |
| Wysa | AIとの対話による感情の整理や、セルフケア・対処スキルの支援 | 悩みの背景について利用者の納得を確認してから、対処方法を提案する | **自分の気持ちや悩みを十分に理解したうえで、納得できる対処方法を選べる** |
| Finch | ペット育成や目標管理を通じたセルフケアの習慣化 | 日々の習慣化よりも、一つの悩みを掘り下げて背景にある要因を探る | **目の前の悩みについて、なぜつらいのかを整理し、具体的な対処につなげられる** |

#### 本サービスならではの提供価値

人間関係の悩みが頭から離れず、自分の目標に向けて行動できなくなっているときに、AIが利用者の心境に合わせて質問を調整し、
感情や価値観への理解を深め、納得できる次の行動を自分で選べるよう支援するサービス。

特に、以下の3つを一連の利用体験として提供する。

1. **言葉にできなくても相談できる**
   選択式と自由入力を併用し、AIが質問を調整することで、利用者のAI活用スキルや言語化能力による負担を軽減する。
2. **AIに決めつけられず、自分の気持ちを理解できる**
   AIの解釈を確認・訂正しながら対話を進めることで、利用者自身が納得できる理解を探る。
3. **自分に合った対処方法を選べる**
   悩みの背景について納得した後に、感情面と問題面の対処方法を提示し、利用者自身が次の行動を選択できる。

これにより、サービスコンセプトである「自分の機嫌は、自分でとれる。」の実現を目指す。

なお、既存サービスにも類似機能が存在する可能性があるため、機能の独自性や優位性を断定するのではなく、本サービスが特に重視する利用体験と提供価値を比較している。記載したメリットは設計上の目標であり、利用者テストで検証する。

### 5-2. 自分が作りたい理由

私自身、AIに悩みを相談した際、自分の気持ちについて複数の選択肢を提示され、どれが近いかを確認された経験がある。しかし、どの選択肢も自分の気持ちとは微妙に違ったり、全く当てはまらなかったりすることがあった。

そのようなとき、提示された選択肢の中から選ばなければ先に進めないように感じ、自分の気持ちをうまく説明できないまま相談をやめてしまったこともある。

AIが気持ちを確認してくれること自体はありがたかったが、用意された選択肢に自分の気持ちを当てはめるのではなく、自分の心境に合わせて対話を進めてほしいと感じた。

そこで本サービスでは、AIの解釈を利用者自身が確認・修正できる仕組みを中心に据えたい。提示された選択肢がどれも当てはまらない場合にも、質問の切り口を変えたり、自由に気持ちを伝えられるようにしたりすることで、利用者が無理なく対話を続け、自分自身の感情や考え方への理解を深められる体験を目指す。

### 5-3. 提供する体験の違い

単に共感や一般的なアドバイスを返すのではなく、悩みの背景にある要因を質問で掘り下げる。AIの仮説に対し「納得できる」「少し違う」「分からない」と回答でき、違いを訂正した場合はAIが確認してから次に進む。**AIが正解を決めるのではなく、利用者が自分の理解を深める過程を支援する**点を特徴とする。

また、AIを使い慣れているかどうかや、気持ちを文章にできるかどうかによって利用しやすさが大きく左右されないことを目指す。選択式と自由入力を併用し、曖昧な回答や「分からない」という回答には、AIが質問を言い換えたり具体例を示したりする。利用者が納得した後には、気持ちを整える方法と状況に働きかける方法を提案し、本人が選べるようにする。

## 6. 提供する価値

### 6-1. 利用者の変化

- **行動**：選択肢や自分の言葉でつらい出来事を表現し、背景を振り返り、自分に合う対処方法を選べる。
- **気持ち**：理解できないつらさを抱え込むだけでなく、自分の反応を少しずつ理解できる。
- **考え方**：出来事そのものと、自分の解釈・感情・価値観を分けて考えられる。

### 6-2. 一文で表す提供価値

人間関係の悩みによって自分の目標に向けた行動が難しくなっている人が、AIの使い方や言語化の得意不得意にかかわらず、
AIと認識をすり合わせながら悩みの背景を探り、自分に合った感情面・問題面の対処方法を選ぶことで、目標に向けた次の一歩を踏み出せるよう支援する。

## 7. MVPと本リリースの機能

### MVP（価値を検証するための最小版）

1. AIとの相談チャット（選択式・自由入力の併用）
2. 回答に応じた質問の調整（言い換え・選択肢・具体例の提示）と、対話を通じた悩みの背景・原因の掘り下げ
3. AIの解釈に対する確認・フィードバック・訂正
4. 利用者の納得後に行う対処方法の提案・選択（感情面・問題面から2〜3案）
5. 現在の相談内容の保存（対話中の文脈や訂正内容を保持するため）


対処方法は「試してみたい」「別の方法がいい」「今は考えたくない」から選べるようにし、提案を押しつけない。利用者がまだ納得していない場合は、対処方法の提案を急がず、対話の継続や終了を選べるようにする。

MVPでは、AIとの対話を通じて利用者が悩みの背景に気づき、自分自身が納得できる対処方法を見つけられるかを検証する。


MVPでは現在の相談内容を保存し、同じ相談内で会話の流れや利用者が訂正した内容を保持できるようにする。
過去の相談履歴を一覧から閲覧する機能はMVP後に検討する。


### MVP後に検討する機能

MVP完成後は、過去の相談履歴を利用者が一覧から閲覧する機能と、AIが過去の相談内容を必要に応じて参照する機能を検討する。特に、AIによる過去の相談の参照は優先して実装したい。

利用者による履歴閲覧では、以前の相談内容や選択した対処方法を自分で振り返れるようにする。

AIによる過去の相談の参照では、以前の相談で確認した感情や価値観、選択した対処方法などを参考にし、今回の悩みとの共通点や変化を探る。

ただし、過去の情報から原因を決めつけず、利用者に確認しながら対話を進める。現在の発言と矛盾する場合は、現在確認された内容を優先する。

過去の相談がなくても、現在の相談だけで深掘りを進められるようにする。

これにより、利用者が自分の感情や考え方の傾向に気づき、継続的な自己理解につなげられるようにする。

その他、対処方法を実践した結果の記録・効果分析、相談傾向の振り返り・分析、日記機能、自己理解の進捗を可視化する仕組みなどを検討する。
相談回数の多さを悩みの深刻さと同一視しない。



## 8. 想定する懸念と対策

| 懸念 | 対策 |
| --- | --- |
| AIが誤った解釈を断定する | 仮説として提示し、利用者の確認・訂正を受ける |
| AIへの指示や言語化が難しい | 選択肢と自由入力を併用し、質問の言い換えや具体例を用意する |
| 利用者が納得する前に対処方法を押しつける | 納得度を確認し、提案の保留・変更・終了を選べるようにする |
| 訂正した内容が次の応答に反映されない | 確認済みの事実・否定された解釈・未確認事項を分けて管理する |
| 過去の相談に引きずられる | 参照前に確認し、現在の利用者の回答を優先する |
| 個人的な相談内容の漏えい | 認証、ユーザー単位のアクセス制御、HTTPS、秘密情報管理、保存・削除方針を設ける |
| 医療的な診断と誤解される | 診断を目的としないことを明示し、必要に応じ専門家への相談を促す |
| API料金や応答遅延 | 使用量を監視し、エラー時の案内や待機表示を用意する |
| 利用者ニーズが不明確 | 架空の相談シナリオによる品質検証と、対象者へのヒアリングを行う |

## 9. 今後の展開

MVPでAIとの深掘り対話と認識のすり合わせが有効かを検証した後、過去の相談履歴を利用者自身が閲覧する機能と、
AIが過去の相談を必要に応じて参照する機能を段階的に追加する。
その後、相談履歴から傾向を振り返れる表示や、日常の気づきを残す日記機能、自己理解の変化を振り返る機能へ拡張する。
高度な類似相談検索は必要性を確かめてから検討する。

| Webフレームワーク | Ruby on Rails | Djangoも可能だが、外部LLM APIを使うためPythonの機械学習ライブラリは必須でなく、Railsでデータ管理・画面更新を一貫して開発しやすい |
| DB | PostgreSQL | MySQLでも基本機能は実現可能。JSONBと将来のpgvector活用の選択肢を考慮 |
| 画面更新 | Hotwire | ReactよりRails中心の構成を維持しやすく、MVPのチャット・訂正画面に適する |
| 認証 | Devise | Rails標準の認証機能と比較し、既存の認証機能を活用して実装負担を抑える。認可は別途実装する |
| 公開先 | Render | AWS（特にEC2を使う構成）よりサーバー管理の負担を抑え、アプリ完成を優先する |
| LLM | OpenAI API | 質問の深さ・訂正への対応・費用・データ取扱条件を検証して最終モデルを選ぶ |

**挑戦したい点**：MVPでは、選択式と自由入力の併用、利用者の回答に応じた質問調整と深掘り対話、仮説へのフィードバック、訂正内容の保存と再利用、納得後の対処方法の提案・選択に挑戦する。MVP完成後は、AIによる過去の相談の適切な参照に挑戦する。

**不安な点**：AIの深掘り品質、解釈の誤り、利用者の納得度を適切に扱えるか、API応答時間、個人情報保護、API・公開環境の料金。

### 10-3. キャッチアップと開発方針

1. RailsとPostgreSQLで認証・相談履歴などの土台を作る。
2. OpenAI APIの基本的な送受信を小さく検証する。
3. Hotwireでチャット画面を段階的に更新する。
4. AIの仮説に対する確認・訂正と、その反映を実装する。
5. 利用者の納得を確認してから、対処方法の提案・選択を実装する。
6. MVPの完成後に、利用者による過去の相談履歴の閲覧機能と、AIによる過去の相談の参照機能を段階的に追加する。



DeviseとHotwireは実装時にRails・Rubyとのバージョン互換性、更新状況、サポート情報を確認する。Renderの無料PostgreSQLは保存期間やバックアップに制限があるため、実データを扱う公開時には適切な有料構成やバックアップ・削除方針を確認する。開発・動作確認には架空の相談データを使用する。
